# E0061: construct with no Go counterpart

The program is well-formed and well-typed, but the Go backend has no way to compile one of its
constructs.

These are real limitations of the backend, not bugs. Known cases: an infinite base set (`Nat`,
`Int` used as a set), function equality, and a multi-component `multicast` filter (a channel
indexed by a tuple). The message names the construct and the reason.

`with (x \in e)` is *not* one of these — it compiles through `Pick` (`runtime/tlaplus/sets.go`), a
uniform-random draw from `e`, the same one a `variable x \in S` initializer already uses. A guard
after the `with` that the draw doesn't satisfy just fails the branch the ordinary way, same as any
other `await`; the block's scheduler retries, redrawing on the next attempt.

## Why it fires

```tla
---- MODULE Example ----
CONSTANTS
    \* @type: Address;
    PID

(*--algorithm Example {
    fifos
        \* @type: <<Address, Address>> -> Channel(Int);
        ch[{PID}];
    process (P = PID) {
    p1: multicast(ch, [m = PID, y \in {PID} |-> 1]);
        goto Done;
    }
}*)
====
```

`ch` is indexed by a pair, so the multicast filter has two components (`m`, `y`). The Go backend
represents a channel's recipients as `map[comm.Address]…`, keyed by a single address — a
tuple-indexed channel has no counterpart. A single-component filter needs no such product and
compiles end to end.

## How to fix it

- Rework the construct into one the backend supports: a bounded set instead of `Nat`, a
  single-binder `multicast`.
- Some cases have no equivalent — check the message; if it names something central to your
  algorithm, the Go target does not fit it.

## See also

- `W0008` — the unsafe casts, which *are* compilable (with a runtime abort on bad input).
